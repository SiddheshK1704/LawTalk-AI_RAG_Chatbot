# LawTalk evaluation & latency metrics

## Terminal metrics (backend)

Run the backend as usual:

```bash
cd backend
uvicorn app.main:app
```

All metrics go to the uvicorn terminal (nothing is shown in the UI):

- On startup: `[STARTUP] model and index loaded in 8.7s`, then a banner with the latest
  `eval/results.json` (if it exists).
- Every request: one line, for example
  `[REQ] /ask/stream embed=0.015s retrieve=0.001s llm_first_token=0.490s llm_total=0.563s e2e=0.581s status=200`
  (`embed=0.000s` means the query embedding came from the cache).
- Every 20 requests (`METRICS_SUMMARY_EVERY`), and on shutdown (Ctrl+C), a summary block with
  request count, error rate, p50/p95 end-to-end latency and per-stage averages.

Backend settings (env vars, all optional): `GROQ_MODEL`, `GROQ_REASONING_EFFORT` (default `low`),
`GROQ_MAX_TOKENS` (1024), `GROQ_TIMEOUT_S` (30), `GROQ_MAX_RETRIES` (2), `LLM_MAX_CONCURRENCY` (8),
`RETRIEVAL_TOP_K` (5), `METRICS_SUMMARY_EVERY` (20).

## Running the evaluation

With the backend running on `http://127.0.0.1:8000`, from the repo root.

**Auth.** The API requires a Supabase session, and the eval does not bypass it. Provide a token for an
existing account in `EVAL_AUTH_TOKEN`. `eval/get_token.py` signs in with `EVAL_EMAIL` / `EVAL_PASSWORD`
and prints one (tokens expire after about an hour). `run_eval.py` checks the token via `GET /auth/check`
before making any LLM calls.

```bash
export EVAL_EMAIL=you@example.com EVAL_PASSWORD=...
export EVAL_AUTH_TOKEN=$(python eval/get_token.py)      # Windows: set EVAL_AUTH_TOKEN=<printed token>
```

```bash
pip install -r eval/requirements.txt   # ragas (eval-only dependency)
python eval/run_eval.py             # full run, ~25 min on the Groq free tier
python eval/run_eval.py --limit 3   # quick smoke test
python eval/run_eval.py --skip-ragas       # retrieval + latency only, no judge calls
python eval/run_eval.py --skip-benchmark   # quality metrics only
python eval/run_eval.py --benchmark-only   # re-measure latency, keep the quality results
```

It prints a results table and writes `eval/results.json` and `eval/results.md`.

| Metric | How it is computed |
|---|---|
| Faithfulness, Answer relevancy, Context precision, Context recall | RAGAS 0.4 (`ragas.metrics.collections`), judge `qwen/qwen3.8-27b` on Groq, on the 20 answerable questions |
| Retrieval Recall@5 / Hit@5 | top-5 chunk IDs vs. the labelled `relevant_chunk_ids` (no LLM) |
| Citation correctness | LLM judge: does each cited passage support the sentence that cites it? (first 10 answers with citations) |
| TTFT p50 | time to first streamed token for the 25 answers |
| p95 latency, request error rate | `eval/benchmark.py`: 30 sequential + 20 concurrent (4 at a time) requests to `/ask` |
| Unanswerable declined | keyword heuristic on the 5 out-of-scope questions |

Answers are produced by the running server (`/ask/stream`), so the real pipeline is evaluated.

### Before/after latency

`eval/baseline.json` holds the benchmark of the original code (commit `c520c93`). To recreate it,
run the original backend on another port and benchmark it:

```bash
python eval/benchmark.py --base-url http://127.0.0.1:8001 --label baseline --no-auth   # original code had no auth
```

`run_eval.py` prints and saves the before/after comparison whenever `eval/baseline.json` exists.

### Test set

`eval/testset.json` (25 questions: 20 answerable, 5 not covered by the documents) is generated by
`python eval/build_testset.py`. Each answerable seed names the source PDF, page and an evidence phrase.
The script then resolves the relevant chunk IDs from `backend/faiss_index` mechanically. If you
rebuild the index, rerun it, because chunk IDs change. Reference answers were drafted by an AI assistant
from the indexed text and have **not** been reviewed by a lawyer (`verified_by_human: false`).

### Notes and caveats

- RAGAS needs `huggingface_hub` to stay at the version used by the backend. If pip tries to upgrade it,
  install with `pip install ragas==0.4.3 "huggingface_hub==1.8.0"`.
- The Groq free tier allows 8,000 tokens/minute per model. Concurrent requests queue (the SDK honours
  `retry-after`) or fail with a 503 `rate_limited` error, which dominates p95 and the error rate.
- The free tier also caps each model at 200,000 tokens/day. A full run uses a large share of the judge's daily budget; if it is exhausted, the run stops with the provider's message rather than waiting. Use `--judge-model` to pick another model.
- 25 questions is a small sample: use these numbers to catch regressions, not as absolute claims.
- Retrieval experiments are recorded in `eval/retrieval_experiments.json` (see the main README for the table).
  A cross-encoder reranker was tried twice and not adopted: lower Hit@5 and ~0.6–0.9 s per query on CPU.

## What changed in the evaluation (this version)

- **Retrieval experiments without API cost:** `python eval/retrieval_experiments.py` compares index and retrieval
  variants on the 20 labelled questions (Recall@5, Hit@5, MRR, retrieval latency) and writes
  `eval/retrieval_experiments.json`. Labels are resolved per index by the same rule as `build_testset.py`, so
  indexes with different chunking are compared on the same evidence. `testset.json` keeps labels for both the
  original index (`relevant_chunk_ids_legacy`) and the rebuilt one (`relevant_chunk_ids`); questions and
  references are unchanged.
- **RAGAS contexts are exactly what the model saw** (source label, any note, text), not raw chunk text.
- **Two judge models share the load:** faithfulness, context recall and citations use `--judge-model`
  (default `qwen/qwen3.8-27b`); answer relevancy and context precision use `--judge-model-2` (default
  `openai/gpt-oss-20b`). One full run needs about 240K judge tokens, more than one free-tier model's 200K/day.
  Judge calls are cached in `eval/.ragas_cache/` so re-runs don't spend tokens again.
- **Provider rate limits are reported separately** from application errors (`App error rate`,
  `Provider rate-limited`), and RAGAS only scores answers that went through RAG mode.
- **`--in-process`** runs the same router, retrieval, prompt and Groq code without HTTP or the auth check, for
  when no `EVAL_AUTH_TOKEN` is available. Results are labelled with the transport used.

## Saving sources with conversation history (optional)

The chat page saves each answer's sources so the evidence panel works when you reopen a conversation.
This needs a `sources` column on the `messages` table (run once in the Supabase SQL editor):

```sql
alter table public.messages add column if not exists sources jsonb;
```

Without the column, answers are still saved and history still works; reopened answers just show no sources.
